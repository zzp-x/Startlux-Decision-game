StartLux-Decision

一套「类型化决策模型」家族:0.8B–27B 稠密模型 + 35B-A3B MoE,支持文本 / JSON / 图像输入、256K 上下文。 每个问题直接返回各选项的概率——不生成任何 token,答案从选项字母的 logits 里"读"出来。

一句话结论

这是一个把大模型当"分类器"用的研究型工程项目:不做自回归生成,而是给每个问题渲染成一份「Evidence / Question / Options」提示词,把选项编成 A、B、C…, 跑一次前向,再在对应字母 token 的 logits 上归一化得到概率分布。整套工程优化(线性注意力快速核、CUDA Graph、共享前缀分块预填充、批处理)都是围绕"单次前向、毫秒级、可当置信度用"这个目标展开的。

仓库本身不含权重,只提供推理代码 + 评测脚本 + 全部原始结果;权重托管在 Hugging Face / ModelScope。

1. 这个项目解决什么问题

传统做法让 LLM 生成答案文本,再解析——慢、且无法直接得到概率。StartLux-Decision 把「决策」抽象成三种类型化问题:

类型含义criteria返回
choice多选一{选项: 说明或 null},最多 26 个choice + confidence + 全选项 probabilities
noul是 / 否可选 {"true":…,"false":…}noul = "是"的概率(无 confidence,等价量是 |2p−1|)
score等级评分按从低到高排列的等级列表(2–10 级)score(概率加权的等级均值)+ confidence + legend

典型场景:客服工单路由、严重程度打分、是否加急、意图分类、工具选择、是否该调用某 API 等——即"需要带置信度的一次性判断"。

2. 核心机制:为什么是"读字母"而不是"生成"

这是整个项目最值得关注的设计。startlux_decision/jevfmt.py(渲染层,VERSION = "jev_render_v3")把一个问题渲染成固定模板:

system : "Apply the criterion to the evidence. Choose exactly one listed option.
          Answer with its letter only."
user   : Evidence:
         <state:字符串 / 自动注解索引的 JSON>

         Question: <instructions>
         Options:
         A) billing: Payments, refunds and invoices
         B) shipping: Delivery and tracking
         C) technical: App, login and account problems
         …(外加 thinking-off 前缀 <think>\n\n</think>\n\n)

然后:只取最后一个位置在 26 个字母 token 上的 logits,除以该问题类型的温度,在已列选项上归一化 → 概率分布。全程 output_tokens = 0。

工程含义:因为不需要生成,延迟只由"输入长度"决定(与输出长度无关),且天然拿到可解释的概率——可以直接当置信度用,也可以设置阈值做兜底/人工复核。同时它使模型对 prompt 格式极度敏感:换一套渲染方式就换一套结果,所以仓库把渲染器版本号(jev_render_v3)写进了代码。

4. 推理引擎关键实现(model.py 精读)

4.1 三类执行路径

路径触发条件做法
CUDA GraphCUDA + graphs=True;1 个问题(长度 128…4096)或 2–4 个问题(每个 ≤1024 token)启动时录制约 40 张图,共用一个显存池;单问题按长度、多问题按 (行数, 长度) 索引。短请求右填充到最近长度后整批重放,消除逐层 kernel 启动开销
Eager 批处理其他请求按长度排序,填充到固定阶梯 PAD_LENGTHS(128…65536),一次前向多行
共享前缀 + 分块同一请求内多个问题的共同前缀 > 4096 token共享段按 32,768 token 分块只跑一次,保留各层 KV / 线性注意力 conv+recurrent 状态;各问题只在尾部跑,通过 log-sum-exp 合并"共享段注意力"与"自身因果注意力"

自研 causal 注意力以 AttentionInterface.register("startlux_causal", …) 注入 transformers:因为输入是右填充、逐层因果,所以不需要 attention mask 张量;融合核优先 cuDNN,退化到 flash。

4.2 值得注意的工程细节

  • 固定填充阶梯而不是精确填充:线性注意力内核按序列长度编译(每个约 1 秒),精确填充会导致几乎每个 batch 都重编译。
  • MoE 走 grouped GEMM:35B-A3B 加载时设 experts_implementation="grouped_mm",每个投影一次 kernel 覆盖所有专家,且不与 host 同步——这样专家层也能被 CUDA Graph 录制。
  • 启动自检:服务启动时同一请求分别跑 graph 路径与 eager 路径,打印最大概率差(六个模型均 0.0);超过 0.02 就丢弃 graphs。
  • 硬性内核依赖:CUDA 上若 flash-linear-attention / causal-conv1d 不可用,StartLuxDecision(...) 直接报错拒绝启动(设 STARTLUX_ALLOW_SLOW=1 可强行跑,但会慢 10 倍以上)。check.py 就是给部署前用的。
  • 宽选项降级策略:wide_choice = {group:25, keep:3, residual:1e-3};>26 个选项时分近等组 → 各组前 3 进决赛 → 其余选项保留 0.1% 残差概率(保证所有选项概率非零)。
  • 置信度严格按 TypeSafe 定义:choice 为 (p_max − 1/n)/(1 − 1/n);score 为"概率加权等级距离"相对均匀分布的归一化、下限 0。作者明确说明 2026-10-03 前返回的是 top 概率,现已更正。
  • 两条吞吐路径:decide() 是延迟路径,decide_batch() 是吞吐路径(跨请求的 12,351 个问题按长度排序打包)。实测 2,678 请求:批处理 140 s vs 逐条 337 s,选项一致率 99.94%(差异来自不同 batch 形状下的 bf16 舍入)。
  • 图像:checkpoint 自带视觉塔;字符串 state 里用 <image> 标记插入位置;每 32×32 像素 1 token,单图上限 1,048,576 像素(1024×1024 ≈ 1024 token);视觉塔每请求只跑一次,图像请求走 eager 路径(不进 graph)。MLX / GGUF 后端只支持文本。

5. 服务与接口

两个服务都用标准库 http.server 实现,对外统一讲 TypeSafe /v1/systemone 协议(所以为 Jev 写的客户端可以无缝切换):

POST /v1/systemone
{"state": {...} | "文本",
 "questions": {"team": {"type":"choice","instructions":"…","criteria":{…}},
               "urgent": {"type":"noul","instructions":"…"},
               "severity":{"type":"score","instructions":"…","criteria":["…","…"]}},
 "images": ["data:image/jpeg;base64,…"]}          # 可选,torch 后端

→ {"answers": {...}, "usage": {"input_tokens":290,"output_tokens":0},
   "model": "…", "latency_ms": 15.7}             # 每个响应带 x-typesafe-request-id 头

GET /health      → {status, model, backend, fast_kernels, cuda_graphs, images, max_length}
GET /v1/models   → {models:[{name, description, release_date}]}
  • 错误码约定:400 请求体格式错误;422 模型无法回答(未知类型、超长 prompt、score > 10 级)。
  • 并发模型:每张 GPU 一次只服务一个请求(threading.Lock),要吞吐就起多个 server + 前面挂负载均衡。
  • gguf_server.py 复用同一个 StartLuxDecision 类,只替换前向:向 llama-server 要全词表 log-probabilities,再按同样温度归一化(与在 logits 上做等价)。自带线程池(--workers 16)、1024 的请求队列。要求 llama.cpp build ≥ b10454。

8. 评测体系

  • eval/fetch_benchmarks.sh:按固定 commit 拉取基准数据(Intern-Decision @2f81580、jevbench @7ce310c7、Typed Decisions @f7a2487e),保证分数可比。Decision Index 套件不可再分发,需用其官方 kit 自行构建。
  • eval/suites.py:七套件 + 校准 pilot,共 10,751 行 / 12,351 个决策;评分直接复用上游 jevbench 的 score_task / brier_score / ece_top_label,并在输出里并列 Intern-Decision README 的数字做对照。支持 --shard i --shards n 多卡分片。
  • eval/typed_decisions.py:400 个案例 × 5 问,对比软标签报 KL / TV / Brier,并明确说明"我们的 Uniform 基线复现了数据集卡片,所以这三项可比,ECE 不可比"。
  • eval/di/:Decision Index 引擎适配 + 多卡批处理 runner + 分片合并,并给出耗时基准(4B 在 5×H200 上约 25 分钟)。
  • eval/latency.py:20 次预热 + N 次计时,报 mean / P50 / P95 与 token 数。
  • results/:287 个原始文件——棋局对战的 PGN 与逐手 JSON、NPC 判定逐句概率、计算机使用逐步日志、汇总 CSV/JSON。可复现性做得比多数同类发布充分。

9. 微调与校准

finetune/finetune_lora.py:每条数据 = 一个请求 + targets(choice 用 criteria 键;noul 用 "true"/"false";score 用 "0"…"n-1")。多人标注可传投票份额作为软标签分布。损失是"目标分布"与"选项字母 softmax"之间的交叉熵——与线上服务时的读出方式完全一致,训练/推理无落差。默认 rank 16 / alpha 32 / dropout 0.05 / lr 1e-4 余弦退火 / 2 epochs;只训 LM 线性层的 LoRA,结束后合并进 runs/mine/merged 作为可直接服务的目录。

finetune/calibrate.py:按问题类型各拟合一个温度(最小化 dev 集 NLL),把结果写回 decision_config.json,并打印 ECE / NLL 前后对比。作者提示了两个坑:dev 集太简单会把温度顶到下界 0.2 导致概率过锐;跨数据源拟合的温度可能过度校正。

实测参考:4B 在 6,000 条合成工单问题上约 3 分钟跑完约 1 个 epoch(含内核编译);27B 的 bf16 权重就要 ~54 GB,需 80 GB 卡。

11. 客观评价:亮点、疑点与风险

值得肯定的

  • 设计思路清晰且少见:"不生成、只读字母"把决策任务从生成式拉回判别式,延迟与输出长度解耦,概率天然可用。
  • 工程完成度高:CUDA Graph、共享前缀分块、融合注意力 LSE 合并、MoE grouped GEMM、固定填充阶梯——每一处都能说出对应的实际瓶颈,不是堆砌。
  • 多后端覆盖完整:CUDA / MLX / GGUF / FP8 四条路,同一套渲染与读出逻辑,便于横向比对。
  • 数据公开透明:287 个原始结果文件、逐手棋谱、逐步日志;评测脚本复用上游评分器并在输出中并列他方数字。
  • 主动披露不利信息:明确说明 ToolACE 无留出集、14 个基准的训练 split 进了训练数据(标 †)、与 Jev 的探索性对局因对方 API key 为空而作废不计、DI 成绩未提交公开榜。
  • 量化损失做了实测:GGUF BF16/Q8_0/Q4_K_M 三档与原权重逐题比对(97–100%),而不是只报体积。

需要打问号 / 注意的

  • 结果全部自报:所有数字由作者自测,Decision Index 未上公开榜,官方 JevBench 分数"不引用";对照系统数值取自公开榜单而非同条件复跑。
  • 数据污染披露但不消除:38 个 DI 基准里 14 个的训练 split 在训练数据中(声称已剔除测试项)——这类"声称已过滤"无法被外部独立验证。
  • 基准设定不利于己的部分也存在:在 GPQA Diamond、MMLU-Pro、BBH、HLE 等知识型基准上明显低于 Jev 1.13(如 MMLU-Pro 66.0 vs 80.5、BBH 71.3 vs 89.7)。项目强在"语言理解 / 检索分类 / 工具调用 / 人类品味",知识推理是短板。
  • 格式强耦合:答案完全依赖渲染模板与字母 token 的切分方式;换 tokenizer 或改模板即需重训/重验,迁移成本高。
  • 极端依赖专用 CUDA 内核:两个内核缺一不可,且 causal-conv1d 常需从源码编译;这在生产环境是个实打实的运维负担。
  • 商用受限:权重 CC BY-NC 4.0,直接排除商业落地(需另行谈授权)。
  • 35B-A3B 覆盖不全:无 GGUF,量化与边缘部署路径缺失。
  • 游戏类结果样本小:作者自己也说"这些任务容易饱和,只当演示、不当基准看"。
